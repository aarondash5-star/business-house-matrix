## Critical security boundaries

1. **Signer trust is independently controlled.** The broker demands a root-owned, non-group/world-writable `/etc/matrix-internal-release/allowed_signers` and a fixed SSH signing identity `matrix-v4-release-owner` in namespace `matrix-v4-host-release`. The Dev Yard worker may not generate the owner's release key or self-install the trust file. No key has been created, requested, installed or copied here.
2. **Approval is not generated by the executor.** The signed canonical JSON must pin the exact V4 source commit, source hashes, QA receipts, host, project, action, short expiry and single-use release ID. The signing key must remain outside the Dev worker's control. A ChatGPT conversation confirmation or GitHub commit authored by the executor does not replace the independent signature.
3. **Only two functions are implemented:** `preflight` and `stage`. The CLI offers `status`, `preflight` and `stage`; preflight currently reports a blocked state until signed approval and proper host enrolment are present. There is deliberately **no `activate` or `rollback` command** in the new broker.
4. **Private stage only.** A successful independently signed stage would create an exclusive single-use reservation and byte-exact V1.3 backup/V1.4 candidate inside a 0700 private journal. It does not write to `matrix-controller`, start a new service, remove the queued task, or alter permissions.
5. **Promotion is still not implemented/certified.** A separately reviewed fixed-purpose host activation runner needs service stop/drain, exclusive lease, bounded installation, restart and independent host rollback. An ordinary SSH shell, site publication `release_check`, or a forged owner approval ledger must not be substituted.
